# nuget-depgraph

Консольная утилита для визуализации графа зависимостей пакета NuGet
(практическая работа №2 по конфигурационному управлению, вариант 16).

## 1. Общее описание

Программа по имени пакета NuGet скачивает метаданные из репозитория
(NuGet API v3, по умолчанию `https://api.nuget.org/v3/index.json`), строит
граф зависимостей с учётом транзитивности и показывает его:

- в виде ASCII-дерева в консоли (`--ascii-tree`);
- в виде текста на языке диаграмм [D2](https://d2lang.com);
- в виде изображения SVG (его создаёт программа `d2` из D2-текста);
- в виде порядка загрузки пакетов (`--load-order`).

Для получения зависимостей не используются менеджеры пакетов и сторонние
библиотеки: запросы делаются стандартными модулями `urllib` и `json`.
Граф строится обходом в ширину (BFS) без рекурсии.

Как выбирается версия: для пакета берётся последняя стабильная версия, для
каждой зависимости — тоже последняя стабильная (диапазоны версий не
разбираются). Зависимости объединяются по всем целевым платформам.

## 2. Требования

- Python 3.8 или новее (только стандартная библиотека);
- программа [`d2`](https://d2lang.com/tour/install) в `PATH` — нужна только
  для создания SVG;
- `make` — по желанию (все команды ниже можно запускать и без него).

## 3. Параметры командной строки

| параметр | описание | по умолчанию |
|----------|----------|--------------|
| `-p`, `--package` | имя анализируемого пакета (обязательный) | — |
| `-r`, `--repo` | URL репозитория NuGet или путь к файлу тестового репозитория (обязательный) | — |
| `-t`, `--test-mode` | режим тестового репозитория: `--repo` — путь к файлу | выключен |
| `-o`, `--output` | имя файла с изображением графа, расширение `.svg` | `graph.svg` |
| `-a`, `--ascii-tree` | вывести зависимости в виде ASCII-дерева | выключен |
| `-d`, `--max-depth` | максимальная глубина анализа (не меньше 1) | 3 |
| `-f`, `--filter` | не учитывать пакеты, в имени которых есть эта подстрока | не задан |
| `-l`, `--load-order` | вывести порядок загрузки (изображение при этом не создаётся) | выключен |

Рядом с SVG сохраняется D2-текст с тем же именем и расширением `.d2`.
Все ошибки (параметры, сеть, формат файла, отсутствие `d2`) печатаются как
`Ошибка: ...` в stderr, код возврата 2 для неверных параметров и 1 для
остальных ошибок.

### Глубина и фильтр

Корень имеет глубину 0. Пакеты на глубине `--max-depth` попадают в граф,
но их зависимости не загружаются. Пакеты, в имени которых есть подстрока
из `--filter`, в анализе не участвуют (регистр важен). Если подстрока есть
в имени корневого пакета, будет ошибка.

### Циклы

Каждый пакет обрабатывается один раз, поэтому цикл не зацикливает
программу. Ребро «назад» остаётся в графе, в дереве такой пакет помечается
`(см. выше)`, а в режиме `--load-order` пакеты из цикла перечисляются в
предупреждении.

## 4. Тестовый репозиторий

С флагом `--test-mode` граф берётся из файла. Формат: на каждой строке
`ПАКЕТ: ЗАВИСИМОСТЬ1 ЗАВИСИМОСТЬ2`, имена состоят из больших латинских
букв, пакет без своей строки считается пакетом без зависимостей. Готовые
файлы лежат в `tests/data/`:

| файл | что проверяет |
|------|---------------|
| `chain.txt` | цепочка A -> B -> C |
| `diamond.txt` | «ромб»: общая зависимость D |
| `cycle.txt` | цикл A -> B -> C -> A |
| `self_loop.txt` | пакет зависит сам от себя |
| `partial_cycle.txt` | цикл B <-> C и независимый пакет X |
| `complex.txt` | граф с циклом B -> D -> F -> B |
| `libs.txt` | имена с общей подстрокой LIB для проверки фильтра |

## 5. Сборка и тесты

Сборка не нужна (Python). Запуск и тесты:

    make run ARGS="-p A -r tests/data/diamond.txt -t -a"
    make test

То же без `make`:

    python3 src/main.py -p A -r tests/data/diamond.txt -t -a
    python3 -m unittest discover -s tests -t . -v

Тесты не требуют интернета и программы `d2`: сеть и запуск `d2`
подменяются.

## 8. Визуализация реальных пакетов NuGet

Три примера для разных пакетов (нужны интернет и установленная `d2`):

    python src/main.py -p Newtonsoft.Json -r https://api.nuget.org/v3/index.json -a -d 2 -o newtonsoft.svg
    python src/main.py -p Serilog -r https://api.nuget.org/v3/index.json -a -d 2 -o serilog.svg
    python src/main.py -p Microsoft.Extensions.Logging -r https://api.nuget.org/v3/index.json -a -d 3 -o logging.svg

Каждая команда печатает ASCII-дерево, сохраняет D2-текст (`newtonsoft.d2`
и т. д.) и изображение SVG. Файлы изображений в репозиторий не
добавляются: они создаются командой выше.

Результаты запусков (вставить вывод дерева и приложить SVG после запуска):

| пакет | глубина | пакетов в графе | вывод |
|-------|---------|-----------------|-------|
| Newtonsoft.Json | 2 | заполнить | заполнить |
| Serilog | 2 | заполнить | заполнить |
| Microsoft.Extensions.Logging | 3 | заполнить | заполнить |

## 9. Сравнение со штатными инструментами NuGet / .NET

Штатный способ получить зависимости (нужен .NET SDK):

    dotnet new console -o check
    cd check
    dotnet add package Newtonsoft.Json
    dotnet restore
    dotnet list package --include-transitive
    dotnet nuget why check.csproj Newtonsoft.Json

`dotnet list package --include-transitive` показывает плоский список
пакетов, а `dotnet nuget why` (в .NET SDK 9 и новее) — пути зависимостей
до пакета. Отдельной штатной визуализации в виде графа в NuGet нет, ближе
всего дерево зависимостей в Visual Studio. Для сравнения нужно открыть
оба результата рядом (вставить вывод в раздел ниже).

Результаты могут отличаться, причины такие:

1. **Целевая платформа.** NuGet берёт только ту группу зависимостей,
   которая подходит проекту (например, `net8.0`). Мы объединяем все группы
   (`netstandard2.0`, `net462` и т. д.), поэтому у нас пакетов обычно
   больше.
2. **Версии.** NuGet выбирает минимальную версию, подходящую под диапазон
   (`>= 1.0.0`), и учитывает правило «ближайшая версия побеждает». Мы
   диапазоны не разбираем и берём последнюю стабильную версию каждого
   пакета, а у разных версий набор зависимостей разный.
3. **Пакеты платформы.** Для современных платформ часть пакетов `System.*`
   уже входит в .NET и менеджер их не скачивает, а в метаданных пакета они
   перечислены, поэтому мы их показываем.
4. **Порядок загрузки.** Менеджер скачивает пакеты параллельно, и порядка
   он не гарантирует. Допустимых порядков может быть несколько (в ромбе
   B и C можно менять местами), мы выбираем один, по алфавиту.
5. **Циклы.** NuGet при цикле выдаёт предупреждение NU1108 и не строит
   порядок, а мы печатаем список пакетов, для которых порядок найти нельзя.
6. **Глубина и фильтр.** У `dotnet` нет аналогов `--max-depth` и
   `--filter`, поэтому для сравнения нужно брать глубину, достаточную
   для всего графа.

Результат сравнения на реальных пакетах (заполнить после запуска): вставить
вывод `-l` и `dotnet list package --include-transitive` и указать, какие из
причин выше объясняют различия.

## 10. Ограничения

- Диапазоны версий не разбираются, берётся последняя стабильная версия.
- Группы зависимостей разных платформ объединяются.
- Имена пакетов сравниваются как строки, регистр в графе не нормализуется.
- Для создания SVG нужна внешняя программа `d2`.
